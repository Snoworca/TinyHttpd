### FR-HTTP-001 — Request.getHeaderEntries returns every request header in received order with duplicates kept

| Field | Value |
| --- | --- |
| Type | functional |
| Target | naruserve-header-contracts |
| Status | verified |
| Priority | high |
| Tags | header-order, naruserve, issue-45 |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

TinyHttpd shall add the default method Request.getHeaderEntries() returning an unmodifiable List<Map.Entry<String,String>> that holds every received request header occurrence once, in the order received, with duplicate names kept at their own positions and each name in the case the client sent.

#### Rationale

NaruServe issue 45: a proxy-style gateway must see interleaved duplicate headers in received order; getHeaders(name) and getHeaderNames() each lose the interleaving. A default method keeps the public 3.0.0 interface source and binary compatible.

#### Acceptance Criteria

- [x] AC-1: A socket test sends the headers Host: x, A: 1, B: 2, a: 3, X-Y: 4 (in this order) and getHeaderEntries() of the handler's Request returns the entries Host=x, A=1, B=2, a=3, X-Y=4 in that order, each name in the case sent.
- [x] AC-2: The returned list and its entries cannot be modified: add, remove and setValue throw UnsupportedOperationException.
- [x] AC-3: RequestWrapper.getHeaderEntries() returns the entries of the wrapped Request unchanged.
- [x] AC-4: getHeader, getHeaders and getHeaderNames keep their results: getHeaders("a") is [1, 3] and getHeaderNames() is [A, B] for the request of AC-1.
- [x] AC-5: The default implementation on Request, for an implementer that does not override it, returns the occurrences grouped by getHeaderNames() order with the values of getHeaders(name), so existing Request implementations keep compiling and answer without a failure.

### FR-HTTP-002 — A non-101 response that sets Upgrade also sends Connection: Upgrade

| Field | Value |
| --- | --- |
| Type | functional |
| Target | naruserve-header-contracts |
| Status | verified |
| Priority | high |
| Tags | upgrade, 426, naruserve, issue-45 |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

When a handler sets a response header Upgrade and the Connection header value Upgrade on a response whose status is not 101, TinyHttpd shall send Connection: Upgrade (Connection: Upgrade, close when the connection closes after the response; Connection: Upgrade, keep-alive on an HTTP/1.0 keep-alive connection) together with the Upgrade header, so a 426 answer is a valid upgrade offer.

#### Rationale

NaruServe issue 45: ExchangeResponse treats Connection as server-managed and ignores every value except close, so the 426 answer of a WebSocket-only path loses Connection: Upgrade although RFC 7231 requires the Upgrade header and RFC 7230 requires Connection: Upgrade beside it.

#### Acceptance Criteria

- [x] AC-1: A socket test whose handler sets status 426, Upgrade: websocket and Connection: Upgrade receives a response with the status 426, the header Upgrade: websocket and a Connection header whose token list contains Upgrade.
- [x] AC-2: When that response also closes the connection (Connection: close requested by the request), the Connection header is Upgrade, close and the connection ends after the body; on an HTTP/1.0 keep-alive connection it is Upgrade, keep-alive.
- [x] AC-3: A Connection value other than close that is set without an Upgrade response header is still ignored: no Connection: Upgrade is sent, as before.
- [x] AC-4: A 101 response of an accepted upgrade keeps its existing Connection: Upgrade handling.
