### FR-HTTP-001 — Request.getHeaderEntries returns every request header in received order with duplicates kept

| Field | Value |
| --- | --- |
| Type | functional |
| Target | naruserve-header-contracts |
| Status | verified |
| Priority | high |
| Tags | header-order, naruserve, issue-45 |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

TinyHttpd shall add the default method Request.getHeaderEntries() returning an unmodifiable List<Map.Entry<String,String>> that holds every received request header occurrence once, in the order received, with duplicate names kept at their own positions and each name in the case the client sent.

#### Rationale

NaruServe issue 45: a proxy-style gateway must see interleaved duplicate headers in received order; getHeaders(name) and getHeaderNames() each lose the interleaving. A default method keeps the public 3.0.0 interface source and binary compatible.

#### Acceptance Criteria

- [x] AC-1: A socket test sends the headers Host: x, A: 1, B: 2, a: 3, X-Y: 4 (in this order) and getHeaderEntries() of the handler's Request returns the entries Host=x, A=1, B=2, a=3, X-Y=4 in that order, each name in the case sent.
- [x] AC-2: The returned list and its entries cannot be modified: add, remove and setValue throw UnsupportedOperationException.
- [x] AC-3: RequestWrapper.getHeaderEntries() returns the entries of the wrapped Request unchanged.
- [x] AC-4: getHeader, getHeaders and getHeaderNames keep their results: getHeaders("a") is [1, 3] and getHeaderNames() is [A, B] for the request of AC-1.
- [x] AC-5: The default implementation on Request, for an implementer that does not override it, returns the occurrences grouped by getHeaderNames() order with the values of getHeaders(name), so existing Request implementations keep compiling and answer without a failure.

### FR-HTTP-002 — A non-101 response that sets Upgrade also sends Connection: Upgrade

| Field | Value |
| --- | --- |
| Type | functional |
| Target | naruserve-header-contracts |
| Status | verified |
| Priority | high |
| Tags | upgrade, 426, naruserve, issue-45 |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

When a handler sets a response header Upgrade and the Connection header value Upgrade on a response whose status is not 101, TinyHttpd shall send Connection: Upgrade (Connection: Upgrade, close when the connection closes after the response; Connection: Upgrade, keep-alive on an HTTP/1.0 keep-alive connection) together with the Upgrade header, so a 426 answer is a valid upgrade offer.

#### Rationale

NaruServe issue 45: ExchangeResponse treats Connection as server-managed and ignores every value except close, so the 426 answer of a WebSocket-only path loses Connection: Upgrade although RFC 7231 requires the Upgrade header and RFC 7230 requires Connection: Upgrade beside it.

#### Acceptance Criteria

- [x] AC-1: A socket test whose handler sets status 426, Upgrade: websocket and Connection: Upgrade receives a response with the status 426, the header Upgrade: websocket and a Connection header whose token list contains Upgrade.
- [x] AC-2: When that response also closes the connection (Connection: close requested by the request), the Connection header is Upgrade, close and the connection ends after the body; on an HTTP/1.0 keep-alive connection it is Upgrade, keep-alive.
- [x] AC-3: A Connection value other than close that is set without an Upgrade response header is still ignored: no Connection: Upgrade is sent, as before.
- [x] AC-4: A 101 response of an accepted upgrade keeps its existing Connection: Upgrade handling.

### FR-HTTP-003 — Response.abort immediately cancels the transport for GET, HEAD and streaming responses

| Field | Value |
| --- | --- |
| Type | functional |
| Target | naruserve-header-contracts |
| Status | verified |
| Priority | high |
| Tags | naruserve, transport-abort, tdd |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

TinyHttpd shall expose a source- and binary-compatible default Response.abort() API. Its engine implementation shall immediately close the connection without generating an HTTP error response, flushing buffered response data or completing chunked framing. Abort shall be idempotent and callable from another thread to unblock socket I/O. ResponseWrapper shall delegate it. Existing Response implementers shall remain compatible through an explicit unsupported default.

#### Rationale

NaruServe HEAD cancellation cannot be represented by a missing response-body byte because HEAD has no response body. An explicit transport cancellation hook is required; it must also wake blocked writers.

#### Acceptance Criteria

- [x] AC-1: For both GET and HEAD, abort before commit closes the transport with no fabricated status line, headers or response body; buffered uncommitted bytes are not emitted, and throwing after abort does not generate a 500 response.
- [x] AC-2: After headers/body bytes have been committed, abort closes the connection without a final chunk or additional response; a pipelined request is never processed on that connection.
- [x] AC-3: Calling abort repeatedly or concurrently is safe; abort from another thread does not wait for a blocked socket writer and causes it to finish with IOException promptly, independently of the configured write timeout.
- [x] AC-4: After abort, body writes and flushes fail with IOException, normal completion sends nothing, and a subsequent unrelated connection remains usable.
- [x] AC-5: ResponseWrapper.abort delegates once per call, and legacy Response implementations continue to compile and use a default abort that throws UnsupportedOperationException rather than pretending cancellation succeeded.
- [x] AC-6: The engine abort contract is exercised on both plain HTTP and TLS, including HEAD; it closes the raw transport without waiting for TLS close_notify.
- [x] AC-7: Aborting a response after its exchange was completed must not close or cancel a later request on a reused keep-alive connection.

### FR-HTTP-004 — Explicit raw request-target policy delegates path validation without weakening transport or decoded-path safety

| Field | Value |
| --- | --- |
| Type | functional |
| Target | naruserve-header-contracts |
| Status | verified |
| Priority | high |
| Tags | naruserve, raw-request-target, issue-59, issue-60, tdd |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

TinyHttpd shall expose RequestTargetPolicy.STRICT and RAW through TinyHttpd.Builder.requestTargetPolicy. STRICT shall remain the default with the existing pre-handler path rejection. RAW shall allow a framework to receive the original undecoded path/query via Request.getRequestURI/getQueryString and decide its own path validity. Request.getPath and built-in consumers of decoded paths shall retain strict decoding/normalization and reject invalid decoded paths through an unchecked validation exception mapped by the engine to HTTP400, without adding checked exceptions to existing public signatures. Transport syntax, Host/body framing validation, static-file containment and existing WebSocket behavior shall remain enforced independently of RAW.

#### Rationale

NaruServe0.10.0 must route/decode/reject original request paths itself. TinyHttpd3.1.0 eagerly decodes paths and rejects them before its handler, blocking NaruServe #59/#60. User authorized SRS updates, TDD implementation, independent review, build and a new patch publication.

#### Acceptance Criteria

- [x] AC-1: With no policy set and with STRICT explicitly set, real HTTP/TLS socket requests to /x/a%2Fb, /x/%00, /x/%2e, /x/%2e%2e and /x/%ZZ return400 before any handler call; /x/ok and /x/a//b reach the handler with unchanged existing decoded-path results.
- [x] AC-2: With RAW explicitly set, every path above, malformed/truncated percent escapes and invalid UTF-8 encodings reaches a raw-accessor handler. getRequestURI/getQueryString preserve literal bytes represented as ISO-8859-1 Strings, slash multiplicity, percent-escape case, plus signs and query delimiters without decoding; origin-form and accepted absolute-form retain their existing extraction semantics.
- [x] AC-3: RAW does not change the existing source-compatible Request.getPath() signature or turn it into an unsafe/nullable decoded accessor: safe paths decode/normalize as before; invalid paths throw an unchecked IllegalArgumentException when getPath is used, and the engine maps this specific validation failure to HTTP400 if uncaught before response commitment, or aborts an already committed response without completing its framing. RequestWrapper delegates these semantics; one server's RAW policy does not affect another server's STRICT policy.
- [x] AC-4: In both policies malformed request lines, literal control/non-ASCII/fragment characters in targets, invalid/missing/duplicate Host, conflicting Content-Length and Transfer-Encoding+Content-Length framing are rejected before handler invocation; invalid framing cannot deliver a subsequent pipelined request to a handler.
- [x] AC-5: Under RAW, built-in static-file serving cannot expose a sentinel file outside its document root through encoded slash/NUL/dot/dot-dot/bad escapes, raw dot segments, double encoding or supported-platform separator/symlink traversal. Safe files still work, and decoded-path router behavior remains strict.
- [x] AC-6: Real WebSocket upgrade and frame exchange still work with STRICT and RAW; invalid decoded paths are not silently normalized into a different WebSocket endpoint or allowed to emit a successful upgrade through a decoded-path consumer.
- [x] AC-7: The policy API is immutable per built ServerConfig, defaults to STRICT and rejects null. HTTP/TLS socket regressions, existing full tests, actual Java8 execution and Android API21 compatibility checks pass without adding dependencies.
